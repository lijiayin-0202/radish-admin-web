# 05｜开发全流程（Web）

> 归属总纲：[AGENT.MD](../AGENT.MD)
> 覆盖：需求 → 方案 → 分支 → 生成 → 编码 → 自测 → 提交 → PR → 联调 → 验收 → 发布 → 复盘

---

## 0. 全流程总览

```
需求(含编号) ──▶ 方案与接口确认 ──▶ 建分支 ──▶ 代码生成 ──▶ 页面编码
      │                                                        │
      │                                                        ▼
  发布复盘 ◀── 线上观察 ◀── 发布/回滚 ◀── 验收 ◀── 自测(测试流1轮=4环节)
                                                ▲
                                        联调/评审(PR) + 后端接口就绪
```

---

## 1. 阶段一：需求澄清（输入：需求 + 编号 + 原型）

| 项 | 要求 |
|----|------|
| 输入 | 需求/Bug 描述、需求编号（`#数字`）、原型图/交互说明、接口约定 |
| 产出 | 需求确认清单（页面清单、字段、状态展示、权限、边界） |
| 红线 | 无编号的 `feat`/`fix` 不允许开工；不编造需求外的页面与功能 |

确认清单模板：
- 涉及哪些页面？列表/详情/表单/弹窗？是否需要新菜单与权限标识？
- 字段来源：后端接口字段是否就绪（swagger 可查）？枚举/字典从哪来？
- 是否有异步链路（Kafka 任务）？状态如何展示与刷新？
- 是否涉及 AI/向量检索结果（`score`）展示与排序？
- 是否需要导出/导入/打印/图表？

---

## 2. 阶段二：技术方案（输出：方案 + 变更清单）

1. 页面清单与路由/菜单路径（`src/view/<模块>/<资源>.vue`）。
2. 接口清单：每个接口的 url、方法、入参、出参、错误码（以后端 swagger 为准）。
3. 文件落点：新增/修改的 `api/*.js`、`view/**`、`components/**`、是否需要字典。
4. 是否可用代码生成器/表单生成器（能生成的一律生成）。
5. 输出【变更文件清单】并确认；涉及新依赖、改构建配置、改框架文件必须 Ask。

---

## 3. 阶段三：分支与环境

```bash
git switch main && git pull
git switch -c feature/xxx      # 或 fix/ opt/ hotfix/ docs/ test/
npm install
npm run dev                    # 确认本地可启动
```

- 业务代码**禁止直推 `main`**；框架类改动单独分支、单独 PR。
- 本地环境：`.env.development` 指向联调后端；代理配置由 `vite.config.js` 提供（改配置属 Ask）。

---

## 4. 阶段四：代码生成 + 页面编码

1. **先生成**：用「系统工具 → 代码生成器（autoCode）」产出列表页与 `api/*.js` 骨架，「表单生成器（formCreate）」产出表单。
2. **再补齐**：
   - `api/*.js`：接口函数，与后端方法一一对应。
   - `view/<模块>/<资源>.vue`：搜索条件、表格列、分页、操作按钮、loading/空态。
   - 表单（`el-drawer`/`el-dialog` 或 `form.vue`）：必填校验、枚举/字典选项、提交与刷新联动。
   - 权限：按钮按后端权限码控制，禁止前端写死权限。
   - 异步/AI 结果：状态轮询或刷新入口，展示后端返回的 `score`/状态。
3. 遵循 `.agent/02`、`.agent/06`、`.agent/07`；不扩大改动面，不新增无关依赖与组件。

---

## 5. 阶段五：自测（测试流执行一轮 = 4 个环节，见 `.agent/04`）

| 环节 | 内容 | 产物 |
|------|------|------|
| 1 | 本地：`npx eslint .` / `npm run build` / `npm run dev` | 终端输出 |
| 2 | Apipost：接口核对（正常/边界/异常/权限），≥3 次 | 用例记录 + 截图 |
| 3 | 浏览器：Console/Network 无报错、功能闭环、双分辨率 | 页面截图 + Console/Network 截图 |
| 4 | 回归：核心链路 + 登录/菜单/权限/字典 | 回归记录 |

**一轮 = 上面 4 个环节**；轮内任一环节失败 → 修复 → 从环节 1 重跑本轮；**测试流执行一轮、项目可正常启动、页面链路跑通无报错即可**，多轮回归按需自测，**非 PR 阻断**。

---

## 6. 阶段六：提交与 PR

```bash
git status                      # 确认无夹带（无 dist/、node_modules/、.env 密钥）
git add <明确文件>               # 禁止 git add .
git commit -m "[feat] [v2.1.0] [#6974499249] 新增客服工单管理页面"
git push origin feature/xxx
```

- 一个 commit 一个类型；混合变更拆分提交（见 `.agent/03`）。
- 冲突按 `.agent/03 §4` 处理，解决后重新 lint + build + 页面验证。
- PR 按模板填写：变更类型、编号、变更文件清单、实现说明、接口清单、菜单配置、自测情况、影响面与回滚。

---

## 7. 阶段七：评审与联调

- 代码评审：分层是否规范、是否复用既有组件、是否有硬编码、字段是否与后端一致、测试是否充分。
- 与后端联调：字段命名（驼峰）、分页字段、枚举字典、错误码提示文案一致。
- 与微服务相关展示：数据由后台接口提供，前端不直连；超时/失败有提示。
- 评审不通过 → 回到阶段四，修复后重新走完整自测。

---

## 8. 阶段八：发布与回滚

1. 发布前：确认后端接口已上线、菜单与权限脚本已执行、环境变量已配置。
2. 发布顺序：后端接口/菜单 → 前端构建产物 → 静态资源刷新（注意缓存与版本戳）。
3. 发布后观察：Console 报错监控、接口失败率、首屏耗时、白屏告警。
4. 回滚预案：回滚前端资源版本（保留上一版产物）、必要时后端菜单回退；**每次发布必须在 PR 中写明**。

---

## 9. 阶段九：复盘与归档

- 更新对接文档（接口清单、菜单路径、权限标识）。
- 复盘记录：问题、根因、改进项（走 `opt` 类型 commit/分支）。
- 文档变更走 `[docs]`，测试补充走 `[test]`。

---

## 10. 各阶段 DoD 速查

| 阶段 | DoD |
|------|-----|
| 需求 | 有编号、有确认清单、接口与字段明确 |
| 方案 | 有页面/接口清单、变更文件清单、依赖改动已确认 |
| 编码 | 生成器产出骨架 + 业务补齐，未改框架底盘 |
| 自测 | 测试流一轮跑通（4 环节全绿），记录截图齐全 |
| 提交 | 格式合规、一次一事、无夹带、冲突已解决并重测 |
| PR | 模板齐全、评审通过、菜单配置说明与回滚方案明确 |
| 发布 | 后端就绪、观察指标正常、回滚预案就绪 |
| 复盘 | 文档更新、改进项有编号有归属 |
